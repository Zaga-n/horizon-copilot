## Context

The repository has OpenSpec scaffolding and one sample Horizon project-management PDF, but no backend or populated index contract. See `proposal.md` for the motivation and the capability specs for observable behavior. The backend must be independently deployable; `local-observability-stack` supplies its local dependencies and telemetry receivers.

## Goals / Non-Goals

**Goals:** one async chat service with durable conversations, a bounded agent, read-only retrieval, and one vendor-neutral telemetry path; one shared `app` migration history across chat and ingestion services.

**Non-Goals:** parsing or embedding source documents inside the chat service, a frontend, asynchronous background continuation of a disconnected stream, and arbitrary agent tools or subagents. `document-ingestion-pipeline` owns extraction and indexing.

## Decisions

### Service boundaries

Use a Python workspace with separate deployable chat, ingestion, and migrations services and one shared `app` schema model package. The one-shot `services/migrations` container owns the single Alembic history used by chat and ingestion, including future ingestion revisions. The chat service has a FastAPI HTTP adapter, application actions for conversations, history, feedback, and turns; typed ports for persistence, retrieval, and agent execution; `db/` for SQL; `genai/` for LangChain behavior; and `bootstrap/` for lifecycle. Routes call one action each. This keeps agent and database SDK types out of the application layer and avoids competing Alembic histories after ingestion is added.

The streaming endpoint is `POST /v1/conversations/{id}/turns:stream` with an SSE-formatted response consumed through `fetch` streaming; native `EventSource` does not support POST bodies. POST /v1/conversations/{id}/turns/{turn_id}:retry takes a failed turn ID, expected failed run ID, and an owner-scoped request key and streams a new assistant attempt. GET /v1/conversations/{id}/turns/{turn_id} exposes reconciliation status; GET /v1/conversations/{id} includes saved thread feedback. Both APIs allowlist the exact configured frontend origin for bearer requests and required methods/headers. Create and list endpoints live under `/v1/conversations`; message history is cursor paginated under `/v1/conversations/{id}/messages`. Per-answer feedback is `PUT`/`DELETE /v1/messages/{id}/feedback`; thread feedback is `PUT`/`DELETE /v1/conversations/{id}/feedback`. The future frontend redirects to Google sign-in and sends its Google ID token as Authorization bearer to both APIs. The configured public OAuth client ID identifies the accepted audience; no custom developer API key or frontend client secret is used, and a Google API access token is not accepted as the identity credential. The principal comes from server-side verification of the ID token's signature, issuer, audience, and expiry; `sub` is the durable external identity, not email. A local-only development identity mode uses a fixed test subject with the API bound to loopback and is rejected by production settings. Every action checks ownership, including feedback, retry, and checkpoint reads.

### Storage, lifecycle, and access

One assistant PostgreSQL database has `app` and `langgraph` as application-owned schemas. The shared Alembic history owns all `app` tables: users, conversations, messages, turns, agent runs, message feedback, thread feedback, documents, document versions, ingestion jobs, upload request mappings, vendor permits, maintenance scheduling records, and document chunks. It uses `include_schemas` plus an `app` allowlist and a schema-qualified version table. Original file bytes live only in MinIO. Document rows contain metadata, SHA-256, pipeline fingerprint, and immutable object references; PostgreSQL holds chunk text/vectors and selective-retry progress. The chat service reads only published chunks from live documents; the ingestion service writes document/version/chunk/job records. Chunks include stable IDs, document version, filename, title (with filename fallback), file type, object reference, page/section heading, text, 1024-dimensional vector, and embedding model/version. Automatic v1 source metadata is limited to those basic fields; automatic project/grant/WP/deliverable extraction and agent-driven metadata filtering are deferred. An upload is not searchable until its version is atomically published. The pgvector extension is a database prerequisite; a migration defines vector and metadata indexes.

LangGraph owns only `langgraph` checkpoint tables. The same migration container runs a separate LangGraph setup step that creates its schema if absent and runs `await AsyncPostgresSaver.setup()` on a dedicated psycopg connection/pool with `search_path=langgraph`, `autocommit=True`, and `dict_row`. This command runs after Alembic and before app readiness, is serialized across deployments, and can be rerun for library upgrades. It is never called from request handling or every app instance startup. Runtime verifies checkpoint schema availability and expected migration level before accepting traffic; no speculative list of LangGraph-owned tables is encoded in Alembic.

Use separate roles: `app_migrator` can alter only `app`; `checkpoint_migrator` can alter only `langgraph`; `chat_runtime` can write chat/feedback tables, read published documents/chunks, and use checkpoint tables; `ingestion_runtime` can write its document/job/chunk tables but cannot read chat messages or checkpoints. Neither runtime role can alter schemas. Revoke broad `public` schema creation and default privileges. Use schema-qualified application SQL and keep the checkpoint pool's search path fixed to `langgraph`. The conversation UUID becomes LangGraph `thread_id` only after owner and active-turn checks succeed.

`app.messages` is a durable display ledger, not a copy of LangGraph state. Store `id`, `conversation_id`, `turn_id`, `attempt_number`, `role`, `content`, `status`, `sources` JSON, timestamps, and ordering key; use UTC database timestamps, FK/indexes, and an idempotency uniqueness constraint. Each source entry stores a citation marker, chunk ID, immutable document-version ID, title, filename, file type, and available primary page/section heading plus the full contributing locator collection, validated against retrieved IDs. Sources are metadata snapshots without restrictive FKs to removable ingestion chunks; after document deletion history preserves the citation and can identify its source as unavailable. `app.message_feedback` holds a unique `(user_id, assistant_message_id)` like/dislike value, nullable dislike comment, and timestamps; a CHECK prevents comments on like values. `app.thread_feedback` holds one editable rating/comment entry per `(user_id, conversation_id)` with timestamps and a server-derived context run/message-order boundary. Rating is nullable for text-only feedback; a CHECK requires rating or nonempty comment. `app.conversations` stores owner, status, timestamps, indexed `last_activity_at`, and active turn/lease fields. Initialize last activity at creation and update it atomically on accepted user turns or explicit answer retries; reads and feedback edits do not extend it. A turn commits its user message and active status before agent execution, then commits one completed assistant message and clears the active turn before sending `completed`. On an error after deltas were emitted, persist the partial assistant attempt with `failed` status and a sanitized reason code, then emit `failed` with a retry target. If bounded terminal-persistence retries cannot reach PostgreSQL, emit `failed` with `persistence_pending=true` and no immediate retry availability; reconciliation after recovery returns the authoritative stored outcome. Persist bounded partial batches before making them visible, keep a bounded process-local failure-intent buffer for prompt repair, and rely on expired active-run leases after a process/replica loss. Pending repair must never downgrade an already committed completion or mutate a newer run. A retry reuses the original user message, creates a new attempt, and excludes failed partial text from the agent prompt. A crash or disconnect is recovered by turn ID and never replays the user input blindly. Per-conversation locking/lease prevents simultaneous graph writes without holding an SQL transaction across model I/O.

### Execution and feedback correlation

Use app.turns for one accepted user input and app.agent_runs for each assistant attempt. Before model/graph execution, start a dedicated OTel run root and atomically persist the turn/user message, reserved assistant message (pending), and run attribution. Allocate a valid root trace ID even when unsampled, independently of inbound browser trace context; link an inbound request span rather than let it collapse multiple runs into one trace. Store run_id (UUID), conversation_id, turn_id, user_message_id, assistant_message_id, attempt_number, 32-character nonzero hexadecimal trace_id, root_span_id, started_at, ended_at, status, safe failure category, retry_of_run_id, and bounded agent/prompt/retrieval configuration versions. Unique (turn_id, attempt_number) and assistant-message/run constraints prevent duplicate attempts; composite FKs or equivalent constraints ensure all joined records belong to the same turn/conversation. Index conversation/time and trace_id. Final persistence updates the reserved assistant row and run together; crash reconciliation terminalizes pending runs without claiming completion. Runtime roles grant chat access to these records only.

Every explicit answer retry starts a fresh run/root trace with retry_of_run_id pointing to the failed attempt; physical model retries stay children. Idempotent retry request mappings preserve the assigned run. History returns run_id/trace_id on assistant entries, and turn status returns user_message_id plus attempt metadata. Message feedback joins through its assistant FK to the immutable run; do not duplicate mutable attribution in feedback payloads. Thread feedback stores context_run_id and a deterministic message-order high-water mark under the same conversation coordination, updating both on an explicit edit. Server validates ownership and excludes purging conversations before feedback writes. Comments are trimmed plain text of at most 4000 Unicode code points; dislike allows null comment, like clears it, and thread feedback permits text-only input.

Runs and feedback cascade with the existing conversation purge, including retry mappings; no longer-lived evaluation dataset is created implicitly. Telemetry retention is independent, so a stored trace_id is a join key rather than proof that a trace exists. Future evaluation can join user input -> turn -> run -> assistant answer -> answer feedback, and use thread feedback's context boundary. Rephrases/corrections/abandonment require a future signal definition and are not automatically labelled as negative feedback.

### Daily conversation retention

Run a cancellable async maintenance task in the chat service lifespan. Typed settings define a positive retention period (default 30 days), a daily UTC schedule, batch size, and lease timing. Persist the last successful scheduled run and coordinate replicas with a database maintenance lease; catch up missed work on startup and recover an expired maintenance lease. There is no blocking background thread and no cleanup on each request.

Select conversations by last_activity_at, not created_at or feedback-driven updated_at. Under the same per-conversation coordination used for turn acceptance, recheck expiry and protect valid active turns, then durably mark the conversation purging. Purging conversations reject reads, turns, retries, and feedback before accessing checkpoints. Recover interrupted turn leases before deciding a conversation is inactive.

For each tombstoned conversation, call await checkpointer.adelete_thread(conversation_id) through the dedicated langgraph pool, then transactionally cascade its messages and source snapshots, answer/thread feedback, turn bookkeeping, and conversation row. Keep the purge marker until both operations succeed; checkpoint deletion and app deletion are separately retryable and idempotent. A failed checkpoint delete cannot be recorded as a successful purge. Cleanup runs in bounded batches without holding a transaction across checkpoint I/O. Chat runtime needs DML/delete privileges for its chat records and checkpoints, never DDL or document mutation privileges.

Retention preserves users, documents, versions, source objects, chunks, successful/failed ingestion results, and upload idempotency state. Document deletion belongs to ingestion. Emit a bounded maintenance trace, completion/failure logs, and low-cardinality purged-count/duration/failure metrics. Verify multi-replica coordination, recent activity in an old conversation, active-turn races, restart recovery, and unchanged document/index rows.

### Agent, retrieval, and safety

Construct the main agent with `create_agent`, one `rag_search` tool, and `AsyncPostgresSaver`. Initialize chat models through `init_chat_model(..., model_provider="bedrock_converse")` using `global.openai.gpt-5.6-terra` for the main agent and `global.openai.gpt-5.6-luna` for guardrail, rewriting, and summarization. Titan `amazon.titan-embed-text-v2:0` produces 1024-dimensional query embeddings. Configure low reasoning effort where the pinned Bedrock Converse integration supports it; probe whether `none` is accepted and use it for simple classifiers only if verified. Do not silently pass unsupported parameters. Pin compatible LangChain and AWS integration versions and run an actual Bedrock smoke test for streamed client-side tool calling, structured guardrail output, token usage, and reasoning parameters before finalizing the factory.

The main model can answer broad Horizon knowledge, but every factual claim about a named project must use RAG; the prompt also favors RAG for work packages, dates, funding, roles, and uncertainty. A bare project name is a three-way scope decision (`in_scope`, `ambiguous`, `out_of_scope`), not a binary reject. A custom async `before_agent` guardrail calls Luna with structured classification, sees only the latest user message plus a short trusted conversation summary, and can produce a clarification or brief scope answer. An explicit prompt-injection classification blocks a malicious request. Model classification is advisory for ambiguous scope, not a guarantee; a deterministic tool allowlist and read-only DB account enforce the hard boundary. Tool results are marked as untrusted data and contain no executable instructions. Citation IDs are validated against returned chunks before answer persistence.

The `rag_search` tool performs one bounded rewrite (or a deterministic fallback to the original query if rewriting fails), one query embedding, and parameterized pgvector similarity search filtered to published shared documents and the caller's own private documents, excluding deleting/deleted document lifecycles. The user/document visibility predicate is applied in SQL before ranking, never supplied by the model. It clamps `k`, total text size, and metadata, deduplicates chunks, and returns chunk IDs, title, filename, file type, document version, page/section heading, score, and bounded excerpts. Basic metadata informs source references in v1 and is stored in queryable fields for future filtering. The tool exposes no metadata-filter argument and does not infer project/WP filters from the query; mandatory authorization/publication/deletion predicates remain enforced. The main agent evaluates that result and may call the same tool again with a different query or `k`; there is no inner retrieval subagent. An inner agent would add a second control loop and make call accounting and terminal behavior less predictable. A maximum of two RAG calls per turn is the initial default, each with at most eight chunks, subject to a total evidence budget.

Use `SummarizationMiddleware` with a token trigger and recent-message keep window, `ModelRetryMiddleware` for transient errors only, `ToolRetryMiddleware` with bounded exponential backoff for transient retrieval errors, custom guardrail middleware, `ToolCallLimitMiddleware(run_limit=2, tool_name="rag_search")`, and `ModelCallLimitMiddleware(run_limit=5)` for the main loop. Internal guardrail/rewrite/summary calls and all physical retry attempts also count against an outer per-turn model-attempt budget and deadline. Reserve final-answer capacity. If a required search exhausts retries, the API supplies a fixed, friendly service-unavailable message, marks the attempt failed/retryable, and logs the technical cause; the model is not asked to invent an outage explanation. A tool-call limit with usable evidence can still yield a qualified answer. No recursion or unbounded retries. Document and test middleware ordering against pinned versions.

### Streaming and telemetry

Use the pinned LangChain/LangGraph async event interface and normalize its model `messages`, graph `updates`, and tool/custom progress into the SSE contract. Event schema includes `event_id`, `conversation_id`, `turn_id`, `run_id`, `assistant_message_id`, `attempt_number`, `type`, and typed `data`; answer deltas carry monotonically increasing sequence numbers. Buffer non-final tool-decision model calls. Stream only a tool-free final-generation phase so guardrail, rewrite, summary, tool-call arguments/results, reasoning, and provisional text are not exposed as answer deltas. This phase must be proven with pinned `create_agent` middleware and Bedrock streaming behavior; do not substitute post-hoc replay of a complete answer. Validate citation markers against the search result set, persist answer and `sources`, then send `completed`. On a started turn's failure, persist the failed attempt and send a sanitized `failed` terminal event with retry metadata. A hard disconnect cannot receive it, so history provides failed status and retry target.

Initialize OTel once in bootstrap. Emit one dedicated answer-attempt run/root span (a fresh trace on explicit retry), physical model attempt spans via a model callback, tool spans from middleware, and retrieval/embedding spans from owned code. Use OTLP push to a Collector for traces and metrics, and structured JSON stdout for logs; Alloy collects logs. The Collector owns projection to Langfuse, so the app does not install a second Langfuse tracing callback. Record model and agent first-chunk timing separately, token usage when provided, bounded fan-out histograms, and retrieval statistics. No per-token spans, high-cardinality metric labels, prompt text, or document text by default. Optional content capture requires an explicit setting and redaction. Keep one trace ID through both destinations.

## Risks / Trade-offs

- **Bedrock support differs by model/API/integration version** → verify streamed tool calls and reasoning settings against the chosen cross-region profiles in an AWS smoke test; fail startup configuration validation for unsupported parameters.
- **Checkpoint and display ledger can diverge after a crash** → persist turn IDs and statuses, serialize conversation turns, reconcile interrupted turns on read/retry, and never claim partial text is complete.
- **Tool-decision and final-answer streaming can conflict** → test the explicit tool-free final phase before release; if the pinned agent cannot separate these phases while streaming, revise the streaming design before implementation rather than streaming provisional text as final.
- **Guardrail classification can misread project names** → represent ambiguity separately and ask a clarifying question; test known and unknown project-name cases.
- **A finite budget can end before sufficient evidence appears** → reserve terminal answer capacity and return uncertainty with available sources rather than looping or fabricating.
- **An empty or incompatible index** → allow empty index with clear no-evidence answers; fail readiness for incompatible dimensions/schema only.
- **A global Bedrock profile can route outside a chosen geography** → expose the inference profile as configuration and document the residency implication before deployment with protected data.

## Migration Plan

On a fresh database, provision roles and pgvector, then run the one-shot migration service container, which applies the shared `alembic upgrade head` for `app` followed by checkpoint setup for `langgraph`. Apply runtime grants and start chat and ingestion only after the container exits successfully. The container ships independently with migration-only credentials; neither runtime service imports or runs it. Future ingestion migrations extend its existing app history. Upgrades repeat that sequence with a compatibility check against the pinned LangGraph version. Rollback deploys previous compatible service versions; destructive schema downgrades and checkpoint table edits are not automatic. Verify fresh replay, Alembic isolation, checkpoint resume, concurrent turns, failed/retried streams, citation persistence, feedback isolation, daily retention/recovery and active-turn races, document preservation, deleted-source exclusion, and an AWS tool/stream smoke test before release.
